# Order-89 skew pool join

These are the programs, plans and driver scripts of the search that found the eleven skew quadruples of order 89 on the board (skew-Hadamard matrices of order 356). The run records are evidence/participants/pool-join/skew-89*.txt. The method is that of research/starter/skew/ (a fixed skew block A invariant under a multiplier group H, windows per block and lag, sampled pools, an exact join), specialised to n = 89 and H of order 11 generated by 2, with faster generators and a join that fits in 28 GB. It is a sampling search, not a census: an empty join proves nothing.

## Files

| file | role | status |
| --- | --- | --- |
| pg2.c | pool generator: annealing with swaps at fixed row sum, AVX2 | exact |
| pg4.c | pg2.c on 16-bit lanes; EP=1 uses the linear energy | exact |
| pgu.c | pool generator: two-stage tabu search or self-avoiding walk, AVX2 byte kernel; same arguments and output as pg2 | exact |
| dedup.c | keeps one row per autocorrelation class modulo H; drops rows outside the plan's windows | exact |
| tj7s.c | the join with SLICE support: rows rechecked against the windows, expanded over H, packed into 2-bit keys per lag, three-way trie join, every leaf rechecked at every lag | exact for round 2, slice 1,0 |
| tj7f.c | tj7s.c with a parallel loader (generated from tj7s.c by a script that is not included) | exact for round 2, slice 2,0, and round 3 |
| n2.txt, w3.txt, b001.txt | plan files: n, A, then for each block its row sum and a window lo hi per lag, then H | exact |
| run_n2.sh, run_w3b.sh | round-1 and round-2 pool generation with pg2 and pg4 | exact; see below |
| round2.sh, r2slices.sh | round-2 generation with pgu and the sliced join with tj7s | exact |
| run3.sh, rest3.sh | round-3 generation, dedup and join | exact |
| chk.py | the independent check of the first solution (reads four rows from sol.txt; skew A, PAF sums, G G^T = 356 I, G + G^T = 2 I) | exact |

The plan in skew-89.txt is w3.txt byte for byte. The round-3 records name n2.txt (generation for blocks 0 and 2) and b001.txt (generation for block 1 and the join).

## How the sources were matched

The run records give no checksums. Every program was built on the run host (16 threads, 28 GB, AMD Zen 4) with `gcc -O3 -march=native -fopenmp -o X X.c -lm` under GCC 16.2.1. Rebuilding each source above with the same GCC and `-march=znver4` gives a binary byte-identical to the one on the run host:

| binary on the run host | md5 | built from |
| --- | --- | --- |
| pg2 | 45d1f46647b6d21a93b70e4f7cba39f4 | pg2.c |
| pg4 | 1cb840497022be630f0435deead7153f | pg4.c |
| pgu (round 2 and round 3) | df04b75de803a4be2bd646c2e4f044cb | pgu.c |
| dedup (round 3) | f02df42a2bcd112c0ac6f1413b547b99 | dedup.c |
| tj7s as first built, kept as tj7s.orig | cc23d1bb558a89f30870e7bfe701fce6 | tj7s.c |
| tj7f (round 3), and tj7s after 2026-11-22 03:24Z | aed4d19966521a8320ceba09c6977280 | tj7f.c |

pg2.c and pg4.c are also identical on the other three hosts that generated round-1 rows.

Which join binary found which solution follows from the timestamps. r2slices.sh ran `./tj7s`. The tj7s.c build was made at 2026-11-22 00:34Z, when the slices started; slice 1,0 ran from 01:20Z to 07:22Z and reported the solution of skew-89.txt. At 03:24Z the file tj7s was replaced by the tj7f.c build (the original survives as tj7s.orig), so slice 2,0, started at 07:32Z, ran tj7f.c and reported the solution of skew-89-slice-2-0.txt at 09:38Z; its log has the per-pool load lines that only tj7f prints. run3.sh built pgu, dedup and tj7f from the files above at 13:59Z and found the nine round-3 solutions with tj7f in slices 1,0, 2,0 and 1,1.

## Command lines

Round 1 (plan n2, four hosts, 2026-11-20 to 2026-11-21) and the start of round 2 (plan w3) generated rows with run_n2.sh and run_w3b.sh and two variants of run_n2.sh that are not included because they hold private host addresses; all of them run exactly these generator commands:

```
KR=300000 ./pg2 n2.txt B n2_hits_B_HOST.txt 0.7 SEED 2000000000        # blocks 0 and 2
EP=1 KR=30000 ./pg4 n2.txt 1 n2_hits_1_HOST.txt 0.45 SEED 2000000000   # block 1
KR=300000 ./pg2 w3.txt B w3_hits_B_HOST.txt 0.7 SEED 2000000000        # round 2, blocks 0 and 2
```

The round-1 union n2_all_B.txt is every host's n2_hits_B file plus any rows those hosts had written under earlier plans, concatenated; the join keeps only rows inside the windows of its plan.

Round 2 on one host, 2026-11-21 23:46Z to 2026-11-22 12:55Z (round2.sh, then r2slices.sh):

```
./pgu w3.txt 0 w3_hits_0_k11.txt 0 SEED 24112320
./pgu w3.txt 2 w3_hits_2_k11.txt 0 SEED 34219424
./pgu n2.txt 1 n2b_hits_1_k11.txt 0 SEED 2090832
cat n2_all_B.txt w3_hits_B_k11.txt n2b_hits_B_k11.txt > r2_all_B.txt   # B = 0, 1, 2; n2_all_B.txt is the round-1 union
SLICE=vb,vc ./tj7s w3.txt r2_all_0.txt r2_all_1.txt r2_all_2.txt     # vb, vc = 0..3
```

Round 3 on the same host, 2026-11-22 13:59Z to 2026-11-23 02:42Z: `R2_0=r2_all_0.txt R2_1=r2_all_1.txt R2_2=r2_all_2.txt ./run3.sh` (the dedup row counts in skew-89-round-3.txt equal the round-3 hits plus these files), which ran

```
./pgu n2.txt   0 r3/core_0.txt 0 SEED+1 125000000
./pgu b001.txt 1 r3/core_1.txt 0 SEED+2 87000000
./pgu n2.txt   2 r3/core_2.txt 0 SEED+3 79000000
cat r2_all_0.txt r3/core_0.txt | ./dedup n2.txt 0 100000000 > r3/A0.txt
cat r3/core_1.txt r2_all_1.txt | ./dedup b001.txt 1 100000000 r3/rest_1.txt > r3/A1.txt
cat r2_all_2.txt r3/core_2.txt | ./dedup n2.txt 2 100000000 > r3/A2.txt
RED=1 SLICE=1,0 ./tj7f b001.txt r3/A0.txt r3/A1.txt r3/A2.txt
```

and stopped after slice 1,0; rest3.sh ran the same join for slices 2,0, 1,1, 2,1, 0,1, 0,2 and 1,2. The seeds are not recorded. Rounds 2 and 3 ran on 16 OpenMP threads.

## Reproducing one hit at small cost

Build with `gcc -O3 -march=native -fopenmp -o X X.c -lm` (AVX2 needed). Ten pool rows for block 0 take a fraction of a second on two threads:

```
OMP_NUM_THREADS=2 ./pgu n2.txt 0 hits0.txt 0 1 10
./dedup n2.txt 0 100 < hits0.txt > /dev/null      # reports 10 rows, 0 not hits
```

A solution needs pools of tens of millions of rows per block and about 10^10 join nodes (hours on 16 threads). The join itself can be checked on one record: put the rows B, C, D of a round-3 solution in three files and join them under b001.txt, which reports that solution (as an image under H) in milliseconds.

```
grep -v '^#' ../../../evidence/participants/pool-join/skew-89-round-3.txt | tr , '\n' > rows.txt
for b in 0 1 2; do sed -n "$((b + 2))p" rows.txt > p$b.txt; done
OMP_NUM_THREADS=2 ./tj7f b001.txt p0.txt p1.txt p2.txt
```

The rows in skew-89.txt are printed after the board's normalisation (row sums -11, 1, -3, 15 in some order); negate rows to row sums 3, 11, 15 and join them under w3.txt.

## Not included

The script that chose the windows of n2.txt, w3.txt and b001.txt is not identified, so the plan files are released as used. tj7b.c (an unsliced round-2 join that ran out of memory) and the round-1 joins tj5.c and tj6.c, which found nothing, are left out.
